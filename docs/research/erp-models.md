## 1. Shopmonkey (public API, v3) — best-documented
Single `Order` object; `status` enum: `Estimate`, `RepairOrder`, `Invoice`. "RepairOrder" is optional (General Settings > Enable Repair Orders). Moving the order into a workflow column converts it (per help snippets). An order has one status at a time. Separate workflow layer: `WorkflowStatus` {name, position, repairOrderWorkflow, invoiceWorkflow, archiveWhenPaid, archiveWhenInactive, daysToArchive, inactiveOrderWarningThreshold, locationId}; order carries workflowStatusId/workflowStatusDate/workflowStatusDuration. Default workflow column names NOT in the API docs.

Order key fields: number, publicId, externalNumber, name, locationId, customerId, vehicleId, serviceWriterId, assignedTechnicianIds[], complaint, recommendation, mileageIn, mileageOut, orderCreatedDate, repairOrderDate, authorized, authorizedDate, completedDate, invoiced, invoicedDate, paid, fullyPaidDate, dueDate, paymentDueDate, paymentTermId, purchaseOrderNumber, statementId, requestedDepositCents, depositFullyPaid, invoiceLockState (Unlocked|Locked|PreviouslyLocked), updatedSinceSignedInvoice, deleted/deletedReason/deletedDate/deletedUserId, archived, imported, appointmentDates[], deferredServiceCount, totals in cents: laborCents, partsCents, tiresCents, feesCents, subcontractsCents, shopSuppliesCents, epaCents, discountCents, taxCents (+ gstCents/hstCents/pstCents), totalCostCents, paidCostCents, remainingCostCents; totalLaborHours, totalAuthorizedLaborHours, completedLaborHours; attributionSource (WorkRequestForm|AppointmentScheduler|Manual|FuzzyCampaignSMSDelivered|FuzzyCampaignEmailRead); taxConfigId; sentToCarfax.

Service (= "job"/"canned job" instance inside an order): authorizationStatus (NotAuthorized|Authorized|Declined), recommended, deferredDate, deferredReason (Archived|Declined|InvoicedNotAuthorized), revived, revivedFromId, sourceServiceId (canned service origin, inferred), pricing (FixedPrice|LineItem), lumpSum, fixedPriceCents, hidden, ordinal, per-service calculated*Cents (labor, parts, tires, fees, shopSupplies, subcontracts, tax, discount, epa), shopSuppliesPercent/ValueType, taxPercent/GST/HST/PST, lineItemOrder (Labor|Part|Tire|Fee|Subcontract), categoryId.

## 2. Tekmetric (UI docs + unofficial OpenAPI; API fields mostly unconfirmed)
Job Board views: "Active", "Saved for Later", "Accounts Receivable", "Paid", "Deleted".
Active columns: "Estimates" -> "Work-in-Progress" -> "Completed".
Estimate statuses (auto): "Not Started", "Requires Authorization", "Pending Authorization", "Declined All". Card actions: "Authorize", "Save for Later", "Delete"; if all declined "Post as Declined".
Authorising >=1 job moves RO to Work-in-Progress (card "Not Started"); WIP "Set Status" options: "In Progress", "Waiting on Parts", "Waiting on Sublet". "Complete Work" -> Completed. Then payment; "Post as Paid" (-> Paid view; reversible via "Unpost"); "Post to A/R" for unpaid (charge accounts/instalments). "Reopen RO" for unpaid ROs. "Posted" matters for reporting (RO counts in reports only once posted — from search snippet).
Unofficial OpenAPI RepairOrder: id, shopId, repairOrderNumber, customerId, vehicleId, repairOrderStatusId (enum values not given), totalSales (dollars, stored cents), createdDate, updatedDate, deletedDate. Deleted ROs only via separate query. Numeric status-id mapping: NOT CONFIRMED.
Other facts: close-ratio metrics depend on advisors using "Post as Declined" instead of Delete; RO Labels (colored) overlay statuses.

## 3. R.O. Writer (docs.rowriter.com v3.0)
RO statuses (default): Open (default; created, converted from estimate or reopened; in WIP), Closed (after full payment processed; not in WIP), On-Hold (WIP), Expected In (customer not yet arrived; WIP), Finished (work done, unpaid; WIP), Void (not in WIP). Up to 10 custom RO statuses; estimates have own fixed status set (Open, deleted option); deleted estimates vanish from History.
RO cannot be deleted; Void clears parts and labor detail but keeps dollar totals; RO number not reused. Estimate -> RO conversion; no separate invoice object (RO "finalized" -> History) (inferred from docs: "Closed" + History).
Reopen: History > Change Status > Open -> back to WIP; stock parts returned to inventory; day sales reversed; payment info lost unless paid electronically (order shows unpaid); A/R charge to customer account is NOT removed, re-finalising creates a second charge; QuickBooks interface can double-post; marketing letter re-sent; "R.O. Reopened Report" exists; scheduler appointment can be re-created.
Parts returns: part on RO has Returned checkbox + reason; stays on RO but not billed; at finalise goes to Part Returns; per-supplier "Process" marks shipped; credit posts as negative AP invoice. Post to Inventory option when part goes back on shelf (with adjustment reason).
Cores: flagged returnable core in inventory; "Core Received With Sale" => customer not charged for core; core statuses Received -> Selected -> Returned (sent) -> Closed out (vendor credit posted to AP). Customer core credit = new RO with "Core Credit" box (credit RO, price 0.00).
Prompts at RO creation: service writer, profit center, purchase order number, mileage.

## 4. Identifix Shop Manager
Default RO statuses (customisable): Checked In, Needs Estimate, Waiting for Approval, Waiting for Parts, Warranty, Completed and Contacted. "An RO in the Estimate phase cannot have a status assigned."

## 5. Mitchell 1 Manager SE
Flow: estimate -> repair order -> invoice -> "Pay/Post Invoice" -> posted to History. Appointment status maps to RO status (release note). Un-Post Invoice exists (password-protectable); a customer/vehicle cannot be removed if open Est./RO/Inv. or A/R balance. License plates unique per vehicle. Duplicate fix = reassign docs, un-post/re-post, delete wrong record. Lowest-numbered customer/vehicle usually original (not always). Converted history tickets must not be un-posted.

## 6. Comebacks (generic)
Fullbay: keep revenue on original invoice and tag as warranty expense instead of credit memo (manual process); charge comeback hours against original tech's efficiency. No vendor docs found with an explicit "original RO id" field. Shopmonkey Payment.paymentType has "Warranty" and "Internal"; Service.sourceServiceId/revivedFromId are the nearest link fields (inferred use).

## 8. 1С:Автосервис 8 (official brochure) and Russian practice
Built on 1С:Управление небольшой фирмой (УНФ). Stated statuses of a repair: "заявка, выполнение ремонта, ожидание, ремонт выполнен, заказ-наряд закрыт" (request, repair in progress, waiting, repair done, work order closed). Documents named: акт осмотра (vehicle inspection act), рабочий лист (shop floor job sheet), заказ-наряд (work order, the main document), квитанция к заказ-наряду (receipt). Stock cycle: заказ покупателя, заказ поставщику (purchase order), поступление (goods receipt), возврат (return), резервирование, реализация (опт и розница) (sale/issue), инвентаризация, списание (write-off). Part movements: выдача со склада под заказ-наряд, возврат на склад, перемещения между заказ-нарядами; "незавершенное производство" (parts held on open work orders = WIP). Free and paid repairs ("платные и бесплатные виды ремонта" - warranty/goodwill); price by model/trim, counterparty, repair kind and place. Time: "планирование и учет рабочего времени, расчет управленческой заработной платы". CRM: предварительная запись на ремонт (booking), "фиксация всех контактов с клиентами" (contact log). Cash/bank: "кассовые и банковские операции" (ПКО приходный кассовый ордер = cash receipt order; ПКО/РКО not named in brochure — from general 1С knowledge, inferred), fiscal registers.
Alfa-Avto (1С-based; via infostart snippets): заявка на ремонт is subordinate to/related with заказ-наряд; fields: причины обращения (reasons for visit), рекомендации сервисного консультанта (advisor recommendations, upsell at approval), акт приема-передачи ТС, выявленные дефекты, дефектовочная ведомость (defect list). Vehicle: марка, модель, год выпуска, гос. номер, VIN, пробег, цвет.
АвтоДилер: module "Сервис"; document states "оформлен или черновик" (posted or draft); filter by предприятие, менеджер, состояние, даты, метки; нормо-часы price = hours x price per норма-час, norms for 80+ marques; акт осмотра, акт дефектовки; счета, акты, УПД (universal transfer doc), дебиторская задолженность.
Generic Russian pipeline (toolfox, partly inferred): заявка -> заказ-наряд (works + запчасти) -> акт выполненных работ -> реализация (sale/issue docs, closes the order, writes off stock) -> оплата (ПКО cash / платежное поручение bank). Mechanic pay is % of work/order/parts at close.
Differences vs US: (a) заказ-наряд is a legal document signed by customer, so no estimate/RO/invoice triplet — one document with status progression and posting ("проведён"); (b) stock is issued to the work order (reservation, issue, return) rather than "parts line" only; (c) money is separate documents (ПКО/РКО, bank) linked to the order, often with advance (аванс) and settlement; (d) нормо-час norm vs actual; (e) legal-entity/ИНН counterparties and УПД/акт paperwork instead of sales-tax lines (VAT/НДС as rate on lines); (f) warehouse moves are documents: перемещение (transfer), оприходование (stock-in), списание.

## 9. Awkward-but-real facts (read vs inferred)
1. Approval is per job/service (Shopmonkey Service.authorizationStatus, Tekmetric per-job authorise; whole RO moves to WIP when >=1 approved; all declined = "Declined All" estimate). Declined jobs become deferred (deferredReason Declined|Archived|InvoicedNotAuthorized); deferredServiceCount on order/customer/vehicle.
2. Estimate/RO/invoice are ONE record with a status enum (Shopmonkey) — not three tables; R.O. Writer has Void keeping totals; Tekmetric "posts" (Paid/A-R/Declined).
3. Payment attaches to a single order; multi-order payments via bulkPaymentId or Statement; deposit flag; refund is a transactionType row plus refundedAmountCents on the original; ~35 free-form paymentType values incl. Account_Receivable, Warranty, Internal.
4. Time: Timesheet.flatRate + laborId/serviceId/orderId, activity General|Order|Service|Labor, type Timeclock|Manual, in addition to Labor.hours (sold) — actual vs sold is two tables.
5. Parts have a two-state life: purchaseStatus (Draft..Received) and inventoryStatus (OnEstimate|InventoryReduced|None); returns/cores are their own rows with status; vendor credit separate from customer refund; R.O. Writer reopen restores stock but not payments.
6. Reopen/un-post effects: payments lost, double A/R charge, double QuickBooks posting (R.O. Writer docs).
7. Stock is per location (InventoryPart.locationId; otherLocationsAvailableQuantity) with InventoryTransfer docs.

## 10. Data-quality mess (sources thin, mostly vendor blogs/forums)
- Duplicate customers/vehicles (Mitchell 1 KB: fix by reassigning, un-post/re-post; can't delete with open docs/A-R). Match on VIN+phone not name (wickedfile/ustech blogs).
- Invalid pasted mileage caused duplicate ROs that couldn't be cancelled (managerforum, snippet); blank mileage blocks reminders.
- Vehicle fields nullable in API: vin, licensePlate, make, model, year all Nullable (Shopmonkey) — vehicles without VIN are first-class. Part: partNumber, sku nullable; name free text.
- Soft deletes with reason (deleted, deletedReason) on order/customer/vehicle; imported flag marks migrated rows.
- NOT found: sources on orders left open for months, "cash customer" placeholder records (inferred common practice).
